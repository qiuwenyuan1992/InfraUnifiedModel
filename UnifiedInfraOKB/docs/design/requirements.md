# OKB v2 需求基线：故障知识图谱与 Agent 诊断记忆底座

日期：2026-11-16。版本：v2 基线（整体取代并删除 v1 全部设计文档）。目标参照：XiHe, *Networked Agent Memory and Causality Representation: Experiences towards Interpretable Cloud-Scale Root-Causing*, SIGCOMM 2026, DOI 10.1145/3789240.3829145。

## 1 系统定位

- OKB 是**故障知识图谱图书馆**：结构化保存带证据出处的因果知识，供诊断 Agent（REST 接口）与运维专家（极简界面）消费。
- 复现 XiHe 的两个资产：**networked causality representation**（透明、可验证的因果图）与作为共享记忆的知识库。知识按需查询、不进 prompt。
- **范围声明（F1）**：OKB 是被动应答的图书馆（lookup / trace / evidence / report 四原语）。诊断 Agent 的会话级工作记忆（当前事故状态、假设、已取证据）与编排层属未来工作，OKB 不做诊断、不做处置、不保存会话状态。

## 2 核心资产：故障知识图谱

```
节点   anomaly_type      异常（GPU ECC 错误、HCA 链路降速等），stable_code 唯一
边     causal_rule       源异常 → 目标异常，携带触发条件、时间约束、反证记录、证据等级
入口   alert_mapping     告警 signature → 候选异常集合（含置信度）
```

- 物理形态：第一期 MySQL 关系表存节点/边/入口，服务内 BFS 遍历；规模达到需要时再导出 NebulaGraph（独立图空间，不碰 UnifiedInfraTopology）。
- 图语义：触发条件不满足的边不可走，防止"可能性"被遍历放大成"必然性"；多跳组合输出显式标注"逐跳已核/组合推导"。

## 3 数据源

| 数据源 | 角色 | 说明 |
| --- | --- | --- |
| `internal_case` | **一等公民** | 已脱敏故障工单/复盘。**结构化程度低，须 LLM 二次结构化提取**（时间线、告警、根因、处置、验证结论），提取结果为候选，须校验后方可入库 |
| `vendor_doc` | 补充源 | 厂商 PDF/HTML/runbook：异常定义、机制解释、可能性枚举 |
| `expert_input` | 补充源 | 专家经验，无出处，最低可信 |
| 反馈数据 | 准确性飞轮输入 | 诊断确认/否决记录（见第 5 节） |

## 4 证据分级

| 等级 | 来源 | Agent 使用规则 |
| --- | --- | --- |
| `case_verified` | 真实工单/复盘提取的已发生因果链 | 可直接入候选链 |
| `doc_explicit` | 厂商文档明示的可能性 | 可入链，输出标注"文档推导" |
| `inferred` | AI 推导 | 仅入人工参考视图，不入 Agent 链 |
| `expert_only` | 专家经验，无出处 | 同上，最低可信 |

证据等级生来自源、不事后提升；用途升级只能通过新证据 + 新修订，禁止反向编造出处。

## 5 准确性机制（三层）

1. **来源定级**：每条知识生来带证据等级（第 4 节）。
2. **抽样审核 + 印证计数（F2）**：案例边以 `draft` 状态入图但带高证据等级；抽样审核比例默认 10%；同一条因果边被 ≥2 个独立工单印证后升 `curated`。非案例边（文档/AI/经验）首次进 `curated` 须专家确认。不做全量人工审核。
3. **运行时反馈飞轮（F3）**：Agent 通过 `report()` 上报诊断使用的边与最终判定（确认/否决）；确认升置信度，否决自动降级并入复核队列；反例同样入库作为反证。

知识状态仅 `draft → curated` 两态；修订历史追加式（每次变更插入新行，不覆盖）。

## 6 安全与脱敏（F4）

- 工单数据已在上游脱敏；OKB 入库前仍做脱敏校验，通过后打 `sensitivity_cleared` 标记，未通过不入库。
- 权限校验做到 **fragment 级**；未授权请求只返回摘要，不返回原文。
- 所有查询与反馈操作记审计。

## 7 交付切片（替代 v1 的 K01—K08 工作包）

| 切片 | 交付 | 验收 |
| --- | --- | --- |
| S0 建馆 | 案例摄取 + LLM 结构化提取 + 证据回链 + 图存储（节点/边/入口）+ 两态修订 | 一份真实脱敏工单变成图上的边，带出处可回查到工单片段 |
| S1 查询 | REST 四原语：lookup / trace / evidence / report + 条件求值 | 输入告警，返回带证据等级、钉住 revision_id 的候选根因链 |
| S2 治理闭环 | 反馈回写置信度 + fragment 级权限 + 专家最小界面（看图/修边/补证据/确认否决） | 确认/否决操作回写边的置信度与状态 |
| S3 按需 | NebulaGraph 导出、多人并发审核、审计细化、MCP 包装 | 真实使用暴露需求后启动，不预先建设 |

顺序约束：**先建馆后查询**——S0 完成前不启动 S1；接口契约可先行冻结文档。

## 8 边界

- 不接实际拓扑/CMDB/资产；知识概念（anomaly_type）不是具体资产；不使用或修改 TopologyDetails.vue、UnifiedInfraTopology 数据库与 NebulaGraph Schema。
- 独立 MySQL 知识库 + 对象存储；独立 Go module。
- 接口形态：**REST 即可，本期不做 MCP**。
- 查询输入是告警 signature / 异常 stable_code，不是资产 ID。
- AI 提候选、人定稿；案例实证 + 抽样 + 反馈替代全量审核。
- stable_code 节点对齐：AI 对新异常候选输出归并建议，人确认，不自动合并。

## 9 与 v1 的差异（丢弃清单）

- 丢弃：不可变发布包、依赖闭包校验、两阶段启用、五状态审核工作流、任务代次/租约、`review_hash` 钉死、K01—K08 横切工作包、契约先行流程。
- 继承：fragment 出处回链 + 固定版本解析、AI 提候选人定稿、三类知识抽象、拓扑隔离、服务端身份与动作授权、stable_code 节点对齐。
- API 响应仍须携带 `revision_id`（F5）：Agent 输出的可复现性要求答案钉住修订版本，即使不再有发布包机制。

## 10 验收场景

- A1 摄取：一份脱敏工单入库，可回查到其结构化提取结果与原文片段。
- A2 提取：AI 提取的因果边带条件、时间约束、证据等级、工单出处。
- A3 印证：同一条边被第 2 个独立工单印证后自动升 `curated`。
- A4 查询：`lookup` 由告警 signature 返回候选异常；`trace` 返回带证据等级与条件求值的候选链。
- A5 反馈：`report` 确认/否决后边的置信度变化，否决边降级入复核队列。
- A6 权限：未授权调用 `evidence` 只拿到摘要。
- A7 对齐：两个厂商别名指向同一 stable_code 节点。
- 每个切片交付时补充真实运行证据；未验证不得宣称通过。
