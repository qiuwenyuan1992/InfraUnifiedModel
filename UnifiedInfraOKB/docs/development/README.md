## 3 切片派发与依赖

切片替代 v1 的 K01—K08 工作包，顺序**先建馆后查询**：

| 切片 | 范围 | 依赖 |
| --- | --- | --- |
| S0 建馆 | 案例摄取（脱敏校验）+ LLM 结构化提取（draft 候选）+ 图存储（节点/边/入口）+ 两态修订 | 无，可立即开始；含 go.mod 初始化、迁移台账、存储与模型适配器 |
| S1 查询 | REST 四原语 + trace 条件求值（facts → passed/failed/unknown） | S0 数据模型稳定 |
| S2 治理闭环 | report 反馈回写置信度 + 专家最小界面（明确清单内改 UnifiedInfraWeb） | S0、S1 |
| S3 按需 | fragment 级权限分级与按动作授权、NebulaGraph 导出、多人并发审核、MCP 包装、审计细化 | 真实使用暴露需求后立项 |

派发要求：每次任务写明基线提交、切片编号、允许路径、禁止路径、覆盖的 A 编号（A1—A7）、验收方式与交付位置。一个任务只负责一个切片或其明确子任务。若只完成 mock、内存仓储或假模型，按实际范围标记部分完成。

## 4 路径与共享文件规则

- 路径以仓库根为准；`OKB/` 简写 `UnifiedInfraOKB/`。默认只能修改本任务允许路径和自己的 `OKB/docs/development/handoffs/<切片>-<主题>.md`。
- 前端修改仅在 S2 范围内按明确清单修改 UnifiedInfraWeb；不得修改 UnifiedInfraTopology、TopologyDetails.vue 或拓扑业务表。
- `go.mod`/迁移编号/公共装配：先由 S0 任务建立并记录，后续变更走交付记录申请，避免并发改写。
- `docs/design/**` 为设计基线：语义变更先更新基线文档再实现，不能借修复顺手改基线。
- 已应用迁移不能改写；追加迁移并记录升级/恢复策略。

## 5 真实依赖与验证

- S0 必须核定 Go 版本、依赖、MySQL 版本、迁移工具、对象存储与模型适配方式，并记录依据；现有拓扑生态可作参考，不能成为 OKB 的隐式运行依赖。
- 开发验证使用独立测试数据库、合成脱敏工单样例与本地/私有对象存储；无获准模型配置时使用固定响应适配器并记录局限。
- 当前尚无 OKB 构建或测试入口，不能声称 `go test`、迁移或服务启动已通过。
- 验收证据至少包括：提交/契约版本、脱敏配置、输入摘要、执行命令与退出结果、关键请求/响应、失败场景与未覆盖项。
- 重点失败路径：脱敏校验未通过、draft 不入查询结果、印证计数不足不升 curated、report 重复上报幂等、修订不可覆盖。
- 公共验收为 A1—A7（见需求基线第 10 节）；不能用"单元测试全通过"代替业务与失败路径证据。

## 6 交付与恢复工作

- 使用 [交付模板](templates/handoff.md) 写入 `handoffs/<切片>-<主题>.md`：已实现/未实现、接口版本、变更文件、迁移、命令结果、风险、下一执行者与输入。
- 任务中断时记录当前工作区、最后成功步骤和失败证据；不把未运行写成通过。
- 接手人先核对实际 diff 与交付记录，再运行与本次任务有关的验证。
