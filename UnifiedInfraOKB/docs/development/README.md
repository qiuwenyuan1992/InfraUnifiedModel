# 开发接手入口

日期：2026-11-16。状态：仅目录骨架与设计交接，尚未进入实现。

## 1 当前事实

- 原有仓库基线为 `main` 的 `9ffbe77635112e03a5430acbd02e829566f932de`；OKB 交付分支为 `docs/okb-foundation`。用户已追加授权提交并推送本套骨架和文档；接手时核对远程分支实际 SHA，不以旧基线代替文档交付版本。
- 现有仓库已有 UnifiedInfraTopology Go 后端和 UnifiedInfraWeb Vue 3 / TypeScript / Element Plus 前端；其现有能力不是 OKB 本轮新增，也未在本轮重新验证部署。
- UnifiedInfraOKB 是同仓库中的独立后端模块，推荐沿用 Go 生态；目录名称只表达职责，不表示已有可运行代码。
- 当前没有 OKB `go.mod`、服务、worker、API、DDL、运行配置、模型调用或知识管理前端；文档中的接口、表和命令均须经后续任务落实。
- 知识正文、修订与审核的权威在独立 MySQL 知识库；原件和大对象另存；Git 保存契约、代码、迁移和合成样例，不能成为专家知识的第二写入口。
- 本期复用 UnifiedInfraWeb 的壳和技术栈，不访问实际拓扑，不修改 `TopologyDetails.vue`、拓扑 DTO、NebulaGraph 或拓扑控制库。

## 2 新执行者的阅读顺序

1. [需求基线与 A01—A14 验收](../design/requirements.md)：先确认产品边界和不可省略的行为。
2. [数据与存储设计](../design/storage-model.md)：区分资料、原件、解析、修订、来源、审核、发布及索引。
3. [流程与界面设计](../design/workflows-and-ui.md)：理解专家操作、冻结点、失败路径和状态呈现。
4. [完整实施计划](plans/2026-11-16-okb-implementation.md)：状态为 planned，按门禁推进，不代表已执行。
5. [工作包与派发边界](work-packages.md)：领取一个有输入、有路径边界、有验收证据的任务。
6. [任务简报模板](templates/task-brief.md)、[交付模板](templates/handoff.md) 和 `handoffs/`：读取前置包的真实交付记录，再开始实现。

需求变更先更新基线和影响任务；实现选择必须符合需求，不能用新代码倒推已经批准了业务语义。

## 3 派发与依赖

工作包顺序：K01 契约/Schema/合成验收 → K02 Go 服务基础/独立存储/身份授权/原件存储接口。
K02 后 K03 资料解析定位与 K05 知识修订审核可并行；K04 主题与候选组装须等 K03、K05 的输入输出接口稳定。
K06 发布查询须等 K05 及 K03 来源接口稳定；K07 可在 K01 后用明确标识的 mock 做页面，但真实完成依赖 K02—K06；K08 在所有实现交付后做真实集成。

“接口稳定”须有契约版本、错误与状态语义、生产者/消费者确认和验证样例，不能只凭目录存在或一条口头约定。
若只完成 mock、内存仓储、固定模型或单元测试，应按实际范围标记部分完成，不能提前关闭依赖包。

每次派发必须复制任务简报模板，写明：基线提交、任务编号、输入契约版本、允许路径、禁止路径、共享文件申请、覆盖的 A 编号、验收方式及交付位置。
一个任务只负责一个工作包或其明确子任务；新增范围须由集成负责人调整任务边界，不能借修复顺手重写其他模块。

## 4 路径与共享文件规则

所有工作包路径以仓库根目录为准，`OKB/` 在工作包中仅简写 `UnifiedInfraOKB/`；新增子目录是计划位置，不表示已经存在实现。
默认只能修改本包的允许路径和自己的 `OKB/docs/development/handoffs/<任务编号>-<主题>.md`；读取依赖代码不受此写入边界限制。
只有 K07 允许修改精确列出的 UnifiedInfraWeb 文件；K08 如发现前端问题，提交证据给 K07 修复，不取得全仓库写权限。
任何包均不得修改 UnifiedInfraTopology、TopologyDetails.vue 或拓扑业务表；不得把知识状态写入拓扑控制库。

| 共享对象 | 单一维护责任 | 下游协作方式 |
| --- | --- | --- |
| `api/v1/**`、`internal/model/**`、字段字典、共享合成样例 | K01 契约负责人 | 提交变更需求及兼容性影响；经确认后由 K01 更新版本和样例 |
| `go.mod`、`go.sum`、公共配置、启动装配、公共路由注册 | K02 基础负责人 | 下游提出依赖或注册项，由 K02 集成，避免并发改写 |
| `migrations/mysql/**`、迁移台账 | K02 迁移负责人 | 各领域包提供表/约束/回填需求；K02 分配唯一顺序号、落盘并验证 |
| MySQL 连接/事务、身份适配、授权、对象存储接口 | K02 基础负责人 | 下游调用约定接口，不另建连接池、口令库或绕过授权 |
| `docs/design/**`、实施计划、开发入口 | 集成负责人 | 领域包报告差异；语义变化协调 K01 更新，避免各包自行改基线 |
| Web 壳、组件注册、包依赖与锁文件 | K07 前端负责人 | 只在允许文件中作必要接入，并验证现有页面 |

共享文件变更应先写入简报的申请区；负责人可直接集成已授权且不改变语义的例行改动。涉及共享语义时，先协调版本和受影响包，再继续依赖实现。
已应用迁移不能直接改写；追加迁移并记录升级/恢复策略。迁移必须使用独立知识库连接、凭据引用和台账，不能复用拓扑库迁移事务。

## 5 独立 checkout 协作

本套材料通过 `docs/okb-foundation` 分支交付；接手前核对远程引用并记录实际提交，不能仅按原有 `main` 基线领取实现任务。用户对本轮骨架/文档提交推送的授权不自动扩展到未来功能任务或主线合并。
后续并行实现使用独立 checkout 或 worktree 和各自分支，从同一已记录基线开始；不要多个 AI 同时编辑同一工作目录。
简报记录 checkout 绝对路径、分支及起点提交；开始前检查工作区状态，不覆盖不属于自己的改动。
任务只交付本包变更和记录；集成负责人按依赖顺序审阅并集成，验证后再推进消费者。提交、合并、推送另依当时授权执行。
发生共享文件冲突时回到维护者处理，不能用保留任意一方文件的方式消除冲突；契约调整须同步生产者和消费者。

## 6 真实依赖与验证

K01/K02 必须核定 Go 版本、依赖、MySQL 版本、迁移工具、身份协议和存储适配，并记录依据；现有拓扑生态可作参考，不能成为 OKB 的隐式运行依赖。
服务与 worker 分进程；生产身份来自获准身份协议，动作权限和审计属于 OKB。测试身份仅在明确开发/测试配置启用。
开发验证使用独立测试数据库、合成文档和私有/本地对象存储；没有获准模型配置时使用固定响应适配器，记录其局限。
PDF 文本层、HTML、人工文本是第一期目标；扫描件/OCR 未实现时必须明确失败或转人工。URL 导入、大小和格式限制由 K01 明确。
OpenSPG/KAG、向量库、实际 CMDB/拓扑均不是本期必装依赖；不得把缺失它们解释为不能编辑既有知识。

当前尚无 OKB 构建或测试入口，不能声称 `go test`、迁移或服务启动已通过。每包实现后须补充实际命令、环境要求和完整结果。
验收证据至少包括：使用的提交/契约版本、脱敏配置、输入摘要、执行命令与退出结果、关键请求/响应或断言、失败场景和未覆盖项。
数据库和文件行为须有真实 MySQL/存储适配验证；HTTP 流程须经过实际服务；前端完成须有真实后端联调，mock 截图不能替代。
公共门禁为 A01—A14；每包责任见工作包清单，跨包场景由 K08 复验。不能用“全部单元测试通过”代替这些业务与失败路径证据。

## 7 交付与恢复工作

使用 [交付模板](templates/handoff.md) 写入 `handoffs/<任务编号>-<主题>.md`，记录已实现/未实现、接口版本、变更文件、迁移、命令结果、风险、下一执行者与输入。
如任务被中断，记录当前工作区、最后成功步骤和失败证据；不要把未运行写成通过，也不要把建议命令写成已执行。
接手人先核对实际 diff 和交付记录，再运行与自己任务有关的验证。只有证据满足包内门禁且集成负责人确认依赖可用，才标记完成。
