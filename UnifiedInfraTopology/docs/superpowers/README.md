# 开发文档治理

本目录保存从权威拓扑模型到可执行代码之间的开发规格与实施计划。

## 权威顺序

出现冲突时，按以下顺序处理：

1. `docs/model/entities/`：实体语义、稳定身份、字段来源和归一化规则。
2. `docs/model/relationships/`：关系语义、方向、合法端点、属性和身份规则。
3. `docs/superpowers/specs/`：跨模型的运行时契约与开发约定。
4. `docs/superpowers/plans/`：经过评审的阶段实施步骤。
5. 当前代码和测试：用于说明现状，不得反向覆盖已确认的新模型。

若高优先级文档存在歧义，先补齐文档并评审，不得在代码中自行选择解释。

## 目录职责

- `specs/`：记录长期有效、可编码、可测试的约束。
- `plans/`：记录一个可独立交付阶段的具体任务、文件、接口、测试和提交检查点。
- Git 历史：承担历史方案与已删除计划的追溯；本目录不保存已废弃文档副本。

## 阶段门禁

每个开发阶段必须按以下顺序推进：

1. 修正并确认 `docs/model/`。
2. 编写或更新对应规格。
3. 编写带复选框的实施计划。
4. 由项目负责人确认规格和计划。
5. 按测试驱动方式逐任务实现。
6. 完成专项测试、全量测试、静态检查和构建。
7. 记录验证证据并提交该阶段。

未经第 4 步确认，不得修改业务代码、数据库迁移、图 Schema、配置或测试。
