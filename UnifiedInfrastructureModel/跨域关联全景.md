# 三域跨域关联全景（2026-11-19 补全）

> 背景：此前 7 组对齐均以服务器为中心（服务器↔网络 4 组、服务器↔动环 3 组），**网络↔动环对齐与三方联动场景空白**——本文件补全为三域全景。
> 用途：图谱层建边的完整设计依据；根因聚合诊断的场景清单（同一物理根因在多域的表征集合）。

## 一、跨域对齐总表（三域 12 组）

| # | 域对 | 编码对 | 关系类型 | 诊断语义 |
|---|---|---|---|---|
| 1 | 服↔网 | `server.nic.link_down` ↔ `net.port.down` | 同一物理事件两面 | 光纤断：两侧同时告 ⇒ 链路本体；单侧 ⇒ 该侧模块/端口 |
| 2 | 服↔网 | `server.optical.*` ↔ `net.optical.perf.degrade` / `net.port.optical_power.*` | 同族（机理同构） | 两侧 DOM 功率对比定位劣化端 |
| 3 | 服↔网 | `server.nic.crc_error` ↔ `net.port.crc_error` | 同族+诊断分流 | 双侧 CRC 升 ⇒ 链路坏；单侧升 ⇒ 该侧问题 |
| 4 | 服↔网 | `server.sys.*`（探活预留） ↔ `net.ping.*` | 语义对齐 | 服务器失联 vs 网络设备失联：带内/带外组合分辨"设备挂 vs 通道断" |
| 5 | 服↔网 | `server.nic.ib.fabric` ↔ `net.ib.*` | 同源（UFM） | cluster_id 相同——同一 UFM 集群事件的两侧观测 |
| 6 | 服↔动 | `server.psu.input_lost` ↔ `power.rack.pdu.output_lost_dual` + 云蜂掉电聚合 | **同一物理事件链** | PDU 双路掉电→机柜掉电→服务器输入丢失；云蜂聚合组对接动环事件 |
| 7 | 服↔动 | `server.liquid.leakage` ↔ `power.cdu.leak` | 同族（源头↔末端） | CDU 漏液先报（源头），服务器漏液传感器后报（末端）；同时报 ⇒ 大范围泄漏 |
| 8 | 服↔动 | `server.thermal.temp.critical` ↔ `cooling.it_room.temp_*` | **因果链上下游** | 机房超温（因）→服务器进风临界（果）；服务器批量 thermal 查机房 |
| 9 | 服↔动 | `server.psu.redundancy_lost` ↔ `power.rack.pdu.output_lost_single` | 同一物理事件两面 | PDU 单路掉电=柜内服务器电源冗余丢失（动环看得见根因） |
| 10 | **网↔动** | `net.device.psu.fault` ↔ `power.rack.pdu.*` / `power.rack.busbar.*` | **同一物理事件链**（**2026-11-19 补**） | 网络设备也吃机柜 PDU/列头柜的电——交换机 PSU 故障先查动环供配电侧（列头柜/PDU 同柜事件） |
| 11 | **网↔动** | `net.device.thermal.alarm` ↔ `cooling.it_room.temp_*` | **因果链上下游**（**2026-11-19 补**） | 机房超温→网络设备温度异常；T0/核心设备超温=机房制冷问题而非设备风扇 |
| 12 | **网↔动** | `net.ping.*.fail`（设备探活） ↔ `power.grid.*`/`power.ups.*`（机房级断电） | **因果链**（**2026-11-19 补**） | 网络设备批量失联先查动环电力（市电/UPS/PDU 链）——设备没挂，是没电了 |

## 二、三方联动场景（根因聚合样板，图谱层核心用例）

### 场景 A：机房级断电（最经典——同一根因三域齐告警）

```
根因：市电中断 power.grid.mains.*（动环）
 ├─ 动环表征：UPS 输入中断 → 电池放电(L1) → 柴发启动事件 → （切换失败则）列头柜/PDU 掉电
 ├─ 服务器域：server.psu.input_lost ×N（整柜/整列）+ 掉电聚合 + server.sys.* 失联
 └─ 网络域：net.device.psu.fault + net.ping.*.fail（设备失联）+ net.port.down（下联口批量）
诊断规则：三域同机房同时窗告警 ⇒ 根因在动环电力链，勿按服务器/网络单域故障处理
```

### 场景 B：机房制冷失效

```
根因：冷机故障/水泵停（动环）
 ├─ 动环：cooling.chiller.fault → 冷通道温度 27→30→35℃ 三档递进
 ├─ 服务器：批量 thermal 临界 + GPU 降频（gpu.perf.degrade/thermal）
 └─ 网络：net.device.thermal.alarm（设备温度）
诊断规则：温度类告警跨 ≥2 域同机房出现 ⇒ 查制冷系统，勿换单机风扇
```

### 场景 C：光链路劣化（既有场景升级为三域）

```
根因：光纤弯折/光模块老化
 ├─ 服务器：server.optical.rx/tx_power.abnormal（DOM）→ nic.crc_error → nic.link_down
 ├─ 网络：net.port.optical_power/BER → net.port.crc_error → net.port.down/flapping
 └─ （若波分链路）net.wdm.* 告警
诊断规则：两侧 DOM 功率+CRC 对比定位劣化端（既有 #1/#2/#3 组合）
```

### 场景 D：机柜掉电（局部版 A）

```
根因：PDU 双路掉电（动环）
 ├─ 动环：power.rack.pdu.output_lost_dual（源头，最先/最准）
 ├─ 服务器：该柜所有 server.psu.input_lost（云蜂掉电聚合自动成组）
 └─ 网络：该柜 TOR 交换机 device.psu.fault → 下联所有端口 down + 服务器失联（网络侧放大）
诊断规则：动环单柜事件 + 网络端口批量 down ⇒ 查该柜 PDU。
⚠️ **修正（2026-11-20 反思）**：原写"动环 30 秒内先到——监控粒度优势"**未验证且很可能相反**——PDU 双路掉电在 dci 侧靠电流归零的**轮询**判定，而服务器侧 psu.input_lost 是 BMC **trap 推送**（事件驱动），推送大概率先于轮询到达。到达顺序待实测，勿据此设计依赖。
```

### 场景 E：集中式冷冻水系统系统性失效（2026-11-19 补，公开案例实证——故障域最大的单域根因）

> 行业实证：香港/新加坡/广州多家头部数据中心因集中式冷冻水系统故障引发 **10 小时级**全机房宕机（华为 2024 能源白皮书）；2022-12 香港案例：**冷却管路漏水进气 → 冷机全面停运 → 温升引发次生消防事故**。

```
根因：冷冻水管路漏水/进气（动环冷却侧系统性失效，非单台设备）
 ├─ 动环：chilled_water.pump_fault / 管路漏水（预留位）→ 多台冷机联锁全停 → 温度三档递进 27→30→35℃
 ├─ ⏱️ 时间压力：蓄冷罐续冷时间是倒计时钟——冷机全停后温升速度取决于蓄冷余量（分钟~小时级）
 ├─ 环境防线：温升可引发次生火灾（env.room.smoke 预留位——香港案例实证 leak→fire 级联）
 ├─ 服务器：批量 thermal 临界 → GPU 降频 → 大面积 perf.degrade → 停机
 └─ 网络：设备温度异常 + （极端）设备损毁
诊断规则：多点温度告警 + 水泵/冷机群告警同时窗 ⇒ 系统性冷却失效（勿换单台冷机）；
⏱️ 处置时钟：蓄冷耗尽前必须恢复供冷——这是三域联动的唯一"倒计时"场景
```

### 场景 F：电网级长时断电（2026-11-19 补，公开风险预警——NERC 2025 冬季评估）

> 行业预警：AI 负载激增推高电网压力（NERC 2025：北美冬季用电 +20GW，数据中心是主要增量）——上游电网风险是动环链之外的系统性风险。

```
根因：外部电网故障/极端天气（动环之上的层）
 ├─ 动环：市电双路中断 → UPS 电池放电（倒计时：分钟级）→ 柴发启动
 ├─ ⏱️ 两级时钟：电池续航（分钟）→ 柴发燃油（小时级：fuel_low 预警是关键前置信号）
 ├─ 兜底链任一环失效（启机失败/ATS 切换失败/燃油耗尽——均为预留位）⇒ 直接升级为场景 A
 └─ 服务器/网络：全链条表征同场景 A
诊断规则：柴发 fuel_low + 电池放电并存 ⇒ 进入长时断电模式（燃油补给优先级最高）
```

### 场景 G：核心网络故障（单域根因的大影响面——公开数据：网络故障频率第五但严重度最高，Uptime Institute 2024）

```
根因：T0/T1 核心交换故障（网络域内）
 ├─ 网络：T0/T1 设备故障/探活失败（单点或双点）
 ├─ 服务器：下联全部 nic.link_down + 批量失联（但 psu/thermal 全正常！）
 └─ 动环：完全正常
诊断规则（**反向规则/阴性对照**）：服务器批量失联 + 动环电力/温度全部正常 ⇒ **先查网络域**——
⚠️ **修正（2026-11-20 反思）**：原规则直接断言"根因在网络域"不完备，还有三个反例：
 ① **批量变更/OS 共因**（固件推送/配置下发让全部服务器 kernel panic——网络设备也全正常）；
 ② **管理面独立故障**（业务正常只是"看起来失联"，见场景 J）；
 ③ **依赖服务挂起**（共享存储/DNS 挂导致服务器无响应但网络完好）。
完整判定序：带内探活通？→ 网络设备自身健康？→ 最近有无批量变更？（变更维度见原则 6）——
三查全过才落"网络域根因"。与"跨≥2域⇒查基础设施"仍构成一正一反，但反规则是**筛查序**不是结论。
```

### 场景 H：液冷 CDU 停机（AI 高密度特有——分钟级温升，2026-11-19 补）

```
根因：CDU 失效（泵停/供电异常——动环）
 ├─ 动环：cdu.pump.fault_secondary / cdu.power.abnormal → 二次侧供液温度升
 ├─ ⏱️ 时间压力：液冷服务器无风冷备份时，温升为**分钟级**（远快于风冷场景 B）——
 │    液冷机柜功率密度 40-100kW+，散热惯性小
 ├─ 服务器：GPU thermal 陡升 → xid 降频/掉卡 → liquid.leakage 伴生（若泄漏起因）
 └─ 与场景 B 的区别：B 走房间级温度（小时级缓冲），H 走供液温度（分钟级）——冷却介质不同，时钟不同
```

### 场景 I：恢复阶段上电风暴（2026-11-20 补——所有场景只写到"故障发生"，恢复期是盲区）

```
根因：场景 A/D 的供电恢复期（故障已结束，二次故障开始）
 ├─ 全部服务器同时上电 → 涌流（inrush） → PDU/列头柜过载**再跳闸**（overcurrent 复发——
 │    同一机柜 10 分钟内掉电→恢复→再超电 = 涌流特征，不是容量债务）
 ├─ 电池刚放完 → UPS 边充电边扛全负载 → 过载/再放电循环
 ├─ 启动风暴：DNS/认证/NTP/存储 等共享依赖被全量并发打挂 → 业务恢复卡在依赖（不卡在电力）
 └─ 诊断规则：恢复 ≠ 结束——overcurrent 在恢复窗复发按涌流处理（分批上电/错峰）；
    "基础设施全恢复但业务起不来" ⇒ 查共享依赖的启动风暴
```

### 场景 J：管理面（带外/MGT）故障（2026-11-20 补——业务无影响但可观测性丧失）

```
根因：管理网交换机（device_role=MGT）故障
 ├─ 服务器：server.bmc.unreachable ×N 批量（带外失联——预留位）——带内业务全正常
 ├─ 网络：MGT 角色设备探活失败；业务网 T0/T1 探活全绿
 ├─ 动环：正常——**且动环是独立系统/独立网络（2026-11-20 拍板），不会随管理面变盲**——
 │    "动环可看+带外盲"反而是管理面故障的佐证（若动环也盲则另有更大范围故障）
 └─ 诊断规则：带内通 + 带外盲 = 管理面问题。
    ⚠️ 优先级悖论：业务零影响但**此时系统处于盲飞状态**——任何新故障都看不见。
    处置优先级应等同 P1（恢复可观测性），而非按"无业务影响"降级。
    另：此场景会**污染场景 G 的判定**（失联可能只是看不见）——G 的筛查序第一步"带内探活通？"即为排除本场景
```

### 场景 K：训练任务慢尾/挂起（超出当前范围——2026-11-20 拍板：未达阈值不关注，场景保留备查）

```
根因：单点劣化拖垮集合通信（straggler 效应）
 ├─ 一张 GPU ECC 可纠正错误频发/降频（gpu.perf.degrade，不触发 P1/P2）→ NCCL all-reduce 全员等它
 ├─ 或一条 IB 链路 symbol error / 降速（net.ib 链路降级占位码）→ 重传 → 通信时间翻倍
 ├─ 表现层：基础设施告警全绿，任务 hang / epoch 时间劣化 / NCCL timeout 日志——只有业务层可见
 └─ 诊断规则：任务级超时 + 基础设施告警全绿 ⇒ 查慢尾：逐卡 perf 指标对比（找离群卡）、
    逐链路 CRC/symbol（找离群链路）。
    ⚠️ 对架构的启示：根因聚合不能只吃"告警"——**指标型劣化（未达阈值）必须作为诊断输入**，
    否则本场景（AI 集群日常）永远诊断不出来。这与"告警驱动"的摄取设计是根本张力。
    （2026-11-20 裁定：当前告警驱动，不做指标摄取；本场景留档，未来若做指标型劣化摄取时启用）
```

### 场景 L：机架级热点（2026-11-20 补——场景 B 的局部版，动环完全看不见）

```
根因：盲板缺失/线缆堆积/风道阻塞（物理环境问题，无任何设备故障）
 ├─ 服务器：同机柜相邻 2-3 台 thermal 递进（房间平均温度完全正常！）
 ├─ 动环：冷通道温湿度全绿——房间级测点密度看不到柜级热点
 ├─ 网络：正常
 └─ 诊断规则：thermal 告警按**机柜空间聚类**（相邻柜位成簇）⇒ 局部气流问题；
    与场景 B 的区分键 = 告警的空间分布（聚类 vs 全散）。
    ⚠️ 依赖：柜级温度测点或 per-server 进风温度——动环侧无此粒度时只能靠服务器侧聚类反推
```

## 二A、公开行业数据校准（2026-11-19，来源：Uptime Institute Annual Outage Analysis 2024 / 华为 2024 能源白皮书 / NERC 2025 冬季评估）

1. **故障根因分布**：电力 37% > 冷却 ~13-20% > IT/系统 > 网络（频率第五）——**与我们三域挖掘深度排序一致**（动环电力链最完整是正确的优先级）
2. **但网络故障严重度最高**（Uptime）：单次影响整机房服务——场景 G 的反向规则因此重要
3. **集中式冷冻水是最大单点故障域**（华为白皮书）：七个子系统、数千米水管、海量接头——场景 E 从"单台冷机"升格为"系统性失效"
4. **第三方/电网风险上升**（Uptime/NERC）：上游依赖不可控——场景 F 把电网级风险纳入
5. **leak→fire 次生级联真实存在**（香港 2022 案例）——印证 env.room.smoke 预留位的必要性

## 三、跨域关联的设计原则（沉淀）

1. **同一物理事件两面/链**（#1/#6/#9/#10）：两码都保留，靠**时间窗+位置（机柜/机房）**关联成边——云蜂掉电聚合、netops 链路 A/B 双端都是现成的边数据源
2. **同族机理**（#2/#3/#5/#7）：编码各建，靠**对比诊断**（双侧 CRC/DOM 功率）消费，不需要合并
3. **因果链**（#4/#8/#11/#12）：上游码是下游的根因候选——根因聚合时上游域事件优先级高于下游表征
4. **根因聚合通用规则**：跨 ≥2 域 + 同机房 + 同时间窗 ⇒ 根因在基础设施层（动环电力/制冷），单域表征勿独立处理；反向筛查（场景 G 判定序）是其补集
5. **位置关联键**：机柜码（cabinet_code）是三域通用主键——dci 告警自带、cloudbee cmdb_extend 自带、netops 告警含机架信息（rack_name）——跨域边全靠它 join。**⚠️ 归一要求（2026-11-20）**：WDM 位置格式不同（`科创-L2-M3-B12-26U-磐石-光`）、IB 无机柜（GUID 对）——join 前需位置归一层
6. **变更维度横切（2026-11-20 补）**：Uptime 数据显示**人为/变更因素是重大宕机的首要贡献者**（占比过半）——但三个监控域都看不到变更。每个场景的诊断第一步都应问"最近什么变了？"（固件/配置/上电操作）——需接入变更/工单数据源，否则场景 G 反例①这类共因故障无法排除
7. **时间窗分级（2026-11-20 补）**："同时间窗"不能一刀切——传播延迟三级：电力事件**秒级**（trap 直推）、液冷**分钟级**（场景 H）、风冷**小时级**（场景 B 蓄冷惯性）。关联窗口按场景设定；且聚合机制会再延迟（alarm_count 累计、故障单生成滞后）
8. **无告警 ≠ 正常（2026-11-20 补）**：采集器自身故障（`net.device.snmp.fault` / `server.bmc.unreachable`）会让故障**隐身**——摄取守门必须有 collector 心跳与数据新鲜度检查；时钟同步（`net.protocol.clock.fault`）是跨域关联的前提，钟歪则窗口失效
9. **冗余丢失态是风险放大器（2026-11-20 补）**：UPS 旁路模式（mode.abnormal）单看是 L3 通知，叠加任何电力异常=灾难（零保护扛浪涌）；N+1 冷机停一台=温度正常但脆弱。冗余态编码要参与**组合判定**而非独立消费——"冗余已失 + 下一事件"应自动升级
10. **告警风暴（2026-11-20 补）**：场景 A 类故障百级告警并发——关联引擎须在风暴下去重/聚合（三域都有现成聚合：云蜂掉电聚合、netops 故障单、dci alarm_count），且**聚合延迟会打乱到达顺序**（见场景 D 修正）

## 四、开放问题裁定（2026-11-20 用户拍板）

1. **存储域**：**并入服务器域**——不独立成第四域；存储相关故障码归 `server.storage.*`（单机盘已覆盖，集群/并行文件系统故障未来按需在该域下扩展）
2. **同源事件到达顺序**：动环**理论上最快**（源头观测），但**消息传送路径不同**（trap 推送/轮询/推送链路各异）——实际到达顺序不保证，**勿按"谁先到"设计依赖**（场景 D 的修正是对的方向；到达顺序只作参考不作判定依据）
3. **动环采集组网**：动环是**独立系统、独立网络**——与带外管理网（MGT）不共网。含义：场景 J（管理面故障）中**动环不会同时变盲**——动环观测独立存活，这反而增强了 J 场景的判定力（管理面挂时动环仍然可看）
4. **指标型劣化（场景 K 类）**：**未达阈值不关注，未来再说**——摄取守门保持"告警驱动"设计；场景 K 的 straggler 诊断不在当前范围（文档保留场景描述，标注"超出当前范围"）

> 以上裁定同步影响：场景 J 判定规则可加"动环可看"作为管理面故障的佐证；场景 K 标注 out-of-scope。
