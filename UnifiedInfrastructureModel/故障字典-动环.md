# 故障字典 · 动环领域（v0.1 初稿）

> 权威源：本文件（Git PR 治理）。数据底稿：raw/dci/dci_strategies.json（74 条，dci-api.prism.jd.local）+ 22 条真实告警样本（机柜容量/液冷/电力类）。
> 编码规则：`power.对象.现象` / `cooling.` / `env.`（动环域下分电力/制冷/环境三个子前缀）。
> **⚠️ DCIM 对象体系（二次挖掘定论）**：策略挂 `device_system`（两大族：电力设施 33 / 暖通系统 23）× `device_type`（冷水机组 12 / 机柜 11 / UPS 系统 9 / 环境温湿度 6 / 列头柜 3 / 变压器 2 / 高压进线柜 2 / 柴油发电机 1 / 精密空调 1）——**液冷 CDU 挂在"暖通系统/冷水机组"下**（与监控点路径"暖通系统--液冷CDU"一致，二次印证）。⚠️ faultTypeId 受控表不可直接跟随：231 是**混合桶**（冷机+液冷 CDU 9 条混编）、132 混装"宿迁单路掉电通知"与"上海列头柜"（L4 通知与 L1 中断两个语义）——**字典编码按策略名/设备对象判定，不按 faultTypeId**。
> 等级：**L→P 定论（既有系统 PowerLevel，权威）**：L1→P0、L2→P1、L3→P2、L4→P3。样本优先原则：电池电压低策略池记 L2、实测 L3，以样本为准。
> 对象层级三级：**机柜列（cabinet_row）→ 机柜（cabinet）→ PDU/测点**——容量类三档（列>柜>测点，层级越高等级越高，2026-11-19 实证）。
> 状态标记：[✓] 已确认 [~] 待评审 [?] 待定。

## 零、与服务器/网络域的跨域对齐（编码前先读）

| 动环域 | 服务器域 | 关系 |
|---|---|---|
| `power.rack.busbar.input_lost` / `power.rack.pdu.output_lost_dual` | `server.psu.input_lost` + 云蜂"单机柜掉电聚合" | **同一物理事件链**：列头柜输入中断(L1)→PDU 双路掉电(L2)→机柜掉电→服务器输入丢失；云蜂聚合组 ↔ 动环事件对接（rack.power.* 边的数据源） |
| `power.cdu.leak` | `server.liquid.leakage` | 同族——CDU 漏液（源头观测）vs 服务器漏液传感器（末端表现） |
| `cooling.it_room.temp_high` | `server.thermal.temp.critical` | 因果链上下游：机房冷通道超温（因）→ 服务器进风温度临界（果）——联动诊断场景 |
| （动环独有：柴发/电池/市电） | 无 | 兜底电源链只到动环层 |

## 挖掘判定记录

- **不进编码**：机房定制（昌金路 24A/宿迁 0 电流 48h——机房名仅是观测面前缀）、CDU 开关机（事件类含计划内操作）、变体（PDU 条数 4/6/8、供电模式正常值 0/1/2——进实例属性）
- **故障与实体整体分析**（2026-11-19 定论）：同一设备实体（冷机/列头柜/电池）的故障不分来源机房前缀（【制冷】【上海】【电气】只是观测面差异）统一编码；策略启停不影响编码语义（沿用三域定论）
- **对象层级三级**：机柜列 > 机柜 > PDU 测点（application 字段 dcim/cabinet_row 是判别键）
- **监控点路径词汇**（DCIM 测点命名）：电力设施--列头柜的支路开关--机柜PDU-A2电流IA2——三段式进观测面，相电流命名（IA1/IB2）进实例属性
- **容量类 vs 故障类分开消费**：over 族（容量债务，长期不恢复，alarm_count 千级）vs outage/掉电族（突发）——映射与诊断策略不同
- **等级链完整**（电力因果链）：市电(L1)→变压器(L1)→UPS输出(L1)/输入(L2)→电池(L4)/柴发(L2)→列头柜(L1-L2)→PDU双路(L2)/单路(L3)→柜超技术峰(L3)/业务峰(L4)→列超电(L2)——从源头到机柜每环有码有等级
- **预留位汇总**（监控空白，字典显影——待监控建设）：电池内阻异常（预测性）、柴发启机失败（兜底失效 L1）、CDU 流量异常（液冷核心工况）、冷冻水供回水温（冷机核心工况）、机房漏水（非 CDU）、STS 切换单元（双总线架构）——六项均标注于对应节
