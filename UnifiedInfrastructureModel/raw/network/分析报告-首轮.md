# 网络域策略池首轮分析（netops.jd.local，2026-11-19）

> 数据：raw/network/netops_strategies.json（312 条，全量）。
> 入口：`POST http://netops.jd.local/api/v1/event-strategy-main/search`（与服务器域同构接口、独立实例——域名 netops vs cloudbee，印证按域分实例）。

## 1. 总体画像：与服务器域根本不同

| 维度 | 服务器域（cloudbee，926 条） | 网络域（netops，312 条） |
|---|---|---|
| 策略组织 | 按**故障部件**（fault_type/fault_parts 完整） | 按**观测指标类型**（category 23 种；fault_type/parts **全空**） |
| 语义载体 | 策略名+trap 编号+XID 码 | category + 策略名（业务/位置语义浓）+ 阈值 |
| 内容构成 | 故障类为主 | **六成是性能/容量阈值**（traffic_* 160、drop/queue 11、cpu/mem 15、ping 16、session 2） |
| 等级刻度 | S1-S4 → P0-P3 | **A1/A3/A5/A7/A9**（奇数五档，全新刻度） |
| 表达式 | path（$.gpu_temp 等 92 种）+ op + value | **无 path**——指标语义在 category，value 即阈值 |

## 2. category 23 种 = 网络域观测词汇表

## 3. 关键发现

### 3.1 网络域探活已建设（与服务器域空白形成对照）
"设备探活"策略 3 条 + [专线接入区]设备探活策略（A1）+ 带外探活（A9）——表达式 `== 0` 断言式。
→ 服务器域 `server.sys.*` 探活预留位在网络域有成熟对应物（带内/带外两级），**跨域探活语义可对齐**。

### 3.2 设备硬件类策略稀少（6 条家族）
板卡重启/主控板切换/电源异常/风扇异常/堆叠异常/端口状态异常——各 1-2 条，走 syslog 类。
→ 网络设备硬件故障（引擎/风扇/电源/板卡）的字典编码可从这 6 条立骨架，深度靠告警样本/工单补。

### 3.3 策略是"业务定制"导向（与服务器域"厂商通配"导向相反）
大量策略绑定具体业务/位置：托管区万国VIVO出口、宿迁五星专线-200M、北京-荷兰专线、商城亦庄移动出口、零售T2队列、金融专线丢包……
→ **"默认策略"与"定制策略"两层结构**：默认策略（端口CRC默认/出口75%默认/CPU85%默认）是领域骨架；定制策略是实例属性（业务/专线/机房），**不进编码**。

### 3.4 表达式阈值类型学（257 条带 op+value）
- 利用率/占比：出口 >75%、CPU >85%、专线超 75%
- 计数类：CRC >= 83 个、drop >33 个、专线丢包 >3
- 断言类：探活 == 0
- **环比/突变类**：出口环比下降80%（<80）、专线流量陡降80%（>0.01）、流量掉零（<99.99）——**突变检测**是网络域特色形态（容量未超但业务受损）
- 绝对带宽：北京-荷兰 >7500Mbps、廊坊联通 >11250Mbps（按专线容量定制的绝对值）

### 3.5 level A 刻度语义（初判待样本验证）
A7=设备硬件类（电源/风扇）、A1=[专线接入区]探活+带宽定制、A9=1/5分钟大数据业务线（疑似低档/高频通知）……
→ 五档语义**不能从策略名定论**，需要告警事件样本验证 A→P 换算。

## 4. 领域字典的范围问题（需拍板）

312 条中真正"故障"语义的是少数；多数是**容量阈值/业务流量监控**。网络域字典范围三选一：
- **A. 纯故障字典**（对齐服务器域定位）：只收 syslog 硬件类+CRC+flaping+探活+drop——约 100 条的策略语义
- **B. 故障+性能双轨**（网络运维实际视角）：加流量陡降/掉零/超阈——丢包和带宽耗尽在网络域就是"事故"，因果链（光模块劣化→CRC↑→丢包→业务卡顿）必须含性能层
- **C. 全收**：连业务专线带宽定制也建码（不建议——那是监控配置不是故障语义）

**建议 B**：网络域的"故障"概念本身就包含性能劣化（这是两个域的领域差异，不是不一致）；业务定制层归实例属性。

## 6 二次挖掘补记（2026-11-19）：策略启停与故障真实性定论

**用户之问**："停用了没关系，策略所描述的故障在网络世界是真实且有意义的吗？"

三层答案（54 条停用策略逐条检验，2026-11-19 二次复核修正）：
1. **真实且该收（绝大多数）**：停用只是监控手段下线，故障本体照常存在——硬件类（主控/电源/风扇）、质量类（包守恒/updown）、性能类停用变体（同类默认策略仍启用：超限 27 条启用/4 停用、掉零 5 启用/1 停用；陡降仅 1 条默认启用/5 条定制停用——陡降观测面现靠单条默认策略支撑，较薄弱）。
2. **不真实不该收（17 条演练工具）**：【测试】前缀的演练/验收策略（出口流量超限测试、CRC测试、DROP测试等），17 条全部停用——非故障语义，正确不收。**⚠️ 区分**："测试区限速1G"（启用中）是**测试机房区域的真实监控**（对象是测试区，策略是活的）——"测试"字样两义：演练工具 vs 测试区对象，按启停+语义判，不按字样判。
3. **监控空白显影（1 例，复核确认）**：`net.traffic.latency`（金融专线延迟异常）停用后**无任何启用替代**（全池"延迟/时延"仅 2 条：金融专线延迟[停用] + 锐捷 updown 异常延迟[flapping 语义，非专线延迟]）——延迟故障真实存在但当前无活探测器。与服务器域探活四预留位同性质：**字典记录真实故障，监控空白由字典显影**（"字典引导监控建设"的第二实例证）。

**字典处理原则定论**：编码语义独立于策略启停——码收"网络世界真实存在的故障"，策略启停只影响"观测面是否有活着的探测器"；停用标注保留为运维参考，不影响码的去留。

## 7 三至五轮挖掘补记（2026-11-19，复合检验/横切面/字段深挖）

### 7.1 第三轮：三层平面复合检验（65 码定稿）
- **补漏 1 码**：`net.protocol.stack.fault` 堆叠异常——"设备堆叠异常"策略一直在池中但首轮漏建码（堆叠分裂=跨成员链路全断）；控制平面十一协议码全齐
- **数据平面四空白建预留位**：ARP/ND 异常、VLAN/VXLAN/EVPN（策略池 0 条整平面空白，AI 集群 overlay 高危）、环路/广播风暴、交换机侧光功率 DOM（跨域同族补位）

### 7.2 第四轮：横切面检验
- **SLA 质量指标族半空白**：丢包/延迟有码，抖动/重传建预留位（金融专线三大 SLA 指标仅覆盖两样；nq_type 值域 pkg_loss(17)/delay(1)/抖动 0 条——数据侧互证）
- **device_role 十四角色体系浮出**：T0-T3 + WE/LE/WR/LR + DE/GR/PR/XR + MGT + server——告警推送过滤维度，进实例属性
- **角色层级序（用户提供定论）**：**T0 < T1 < T2 < LE/WE < WR < PR/GR**（核心→叶子/东西向→出口→骨干/汇聚，越高离核心越远影响面越大）

### 7.3 第五轮：字段深挖（从未碰过的字段）
- **波分等级错配根因破解（悬案结案）**：wdm 策略带 `bofen_level=['CRITICAL','MAJOR']` 过滤字段——netops 只按厂商等级词过滤"收不收"、**未做等级映射**，落库统一 A9。修法明确（按 bofen_level 映射 A 档），非数据源缺陷
- **告警升级链（repeatUpgrade 5 条）**：CRC/端口状态/BGP 挂【升级-重复】衍生策略——同故障持续不恢复自动抬档；摄取时按 basicId 归并同码

- **通知体系（notices 287 条）**：广泛存在但与故障语义无关，不进字典
