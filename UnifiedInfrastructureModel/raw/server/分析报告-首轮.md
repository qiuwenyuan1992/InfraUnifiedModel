# Cloudbee 故障策略数据首轮分析（服务器领域）

- 数据源：`http://cloudbee-api.jd.local/api/v1/event-strategy-main/search`（fetch_cloudbee_strategies.py 全量抓取）
- 抓取时间：见 fetch_meta.json；总量 926 条，按 id 去重后 926 条
- 原始数据：cloudbee_strategies.json（只进不改）

## 1 核心发现

1. **受控词汇已存在**：`fault_type`（19 种）+ `fault_parts`（19 种）就是服务器领域的故障类型受控表——字典的骨架不用发明，直接以它为底。
2. **策略名粒度达 stable_code 级**：GPU 领域已细分到 XID 48/79/95/119/120/149、显存 ECC、HCCS 链路、NVLink P2P、掉件、温度等——同一 fault_type 下有明确的子类型结构（监控来源×错误码×部位）。
3. **策略名自带结构**：`带内-syslog-GPU-xid` = 数据通路（带内/带外）×来源（syslog/Exporter/snmptrap）×对象×具体错误——可作为编码派生规则。
4. **等级/状态齐全**：S1-S4 四级（S1 严重占 57%）——severity 可直接映射。

## 3 映射建议（cloudbee → OKB 字典）

### 3.1 领域与 stable_code 前缀

| cloudbee fault_type | OKB 领域 | stable_code 前缀建议 |
|---|---|---|
| GPU故障 | gpu | `gpu.` |
| 硬盘/SSD写穿 | storage | `storage.disk.` / `storage.ssd.` |
| 内存故障 | server | `server.memory.` |
| 电源故障 | power | `server.psu.`（服务器侧电源，区别于 `rack.power.`） |
| CPU故障 | server | `server.cpu.` |
| 风扇故障 | server | `server.fan.` |
| 主板故障 | server | `server.board.` |
| 阵列卡故障 | storage | `storage.raid.` |
| 网线/网卡/光模块 | network | `net.cable.` / `net.nic.` / `net.optical.` |
| PCI故障 | pcie | `pcie.` |
| 电池故障 | server | `server.battery.`（RAID/CMOS 电池细分） |

### 3.2 severity 映射

S1-严重→P1 / S2-高→P2 / S3-中等→P3 / S4-低→P4

### 3.3 策略名 → 子类型拆解规则（GPU 示例）

策略名结构：`[通路]-[来源]-[对象]-[错误]
`
- XID 错误码独立成码：`gpu.xid.48`、`gpu.xid.79`…（NVIDIA XID 错误码表是现成的 TBox 参照）
- ECC 细分：`gpu.ecc.vram.multi_bit`（显存多比特）等
- 结构性故障：`gpu.hccs.link.error`、`gpu.nvlink.p2p.error`、`gpu.slot.drop`（掉件）
- 温度：`gpu.temp.limit`（Tlimit）

## 4 待定问题（需你拍板）

1. **GPU 与 NPU 并存**：策略里有 NPU（昇腾）——字典是否单列 `npu.` 领域？建议：单列（与 GPU 分开，语义不同）。
2. **带内/带外通路是否进编码**：建议不进 stable_code（同一故障带内带外都能发现，通路属于“观测面”字段，不是故障本体）。
3. **XID 码表来源**：建议以 NVIDIA 官方 XID 文档为准生成子码，策略名只是线索。
4. **触发条件表达式普遍为空**：本轮无法提取告警触发条件语义；后续可从有表达式的策略补。
5. **二级/三级事件分类全为“-”**：该系统未用这两级分类，可忽略。
